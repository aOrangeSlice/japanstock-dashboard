# 日股工作台 · 云部署说明（方案 A：GitHub Actions + Pages + Release）

> **文档日期**：2026-10-03 ｜ **状态**：本地就绪，待推送后启用
> **架构**：GitHub Actions（计算）+ GitHub Release 资产（SQLite 持久化）+ GitHub Pages（托管）

---

## 1. 架构与数据流

```
GitHub Actions cron（UTC）
  02:45 = JST 11:45 前場引け → sync --session noon
  06:45 = JST 15:45 大引け後 → sync --session close
        ↓
  ① 从 Release 标签 db-snapshot 下载 japanstock.db（无则 init + backfill 全量重建）
  ② pipeline_jp.py sync（is_trading_day() 自动跳过祝日）
  ③ render_jp.py 渲染 HTML
  ④ node tools/check_dashboard_jp.js 四步校验（硬门禁，失败不部署）
  ⑤ WAL checkpoint 后把 japanstock.db 上传回 Release（--clobber）
  ⑥ HTML 部署到 gh-pages 分支（force orphan，单 commit 不膨胀）
        ↓
  GitHub Pages（https://<user>.github.io/japanstock-dashboard/）
```

要点：
- **cron 是 UTC**，日本无夏令时，偏移固定；`1-5` 挡周末，祝日由代码守卫兜底
- **db 不进 git**（二进制全量 diff 会撑爆仓库），走 Release 资产（单资产上限 2GB，当前仅 16.4MB）
- **gh-pages 每次强制 orphan commit**，仓库体积不受每日部署影响
- 每次 gh-pages 部署都会产生 commit → 仓库保持活跃，**不会触发 Actions 定时任务 60 天自动停用**

## 2. 首次启用清单（按顺序）

| # | 操作 | 说明 |
|---|---|---|
| 1 | 推送 main 分支到公开库 `japanstock-dashboard` | 本地已 commit，待授权后推送 |
| 2 | **手动触发一次 workflow**（Actions → jp-sync-deploy → Run workflow，session 留空） | ⚠️ 关键验证点：观察 yfinance 在 GitHub 机房 IP 下是否 429。首次运行无 Release 资产，会自动 init+backfill（约 10~40 分钟） |

| 5 | 打开 Pages URL 验收（数值与本地版对拍） | — |
| 6 | 停用本地两条定时任务（11:45 / 15:45） | WorkBuddy 自动化里手动关闭 |

## 3. 运维须知

- **失败告警**：workflow 失败时 GitHub 默认发邮件到账号邮箱，无需额外配置
- **手动重跑**：Actions → Run workflow；session 留空按 UTC 时段自动判定（<05 时 = noon）
- **数据断档排查**：先看 Actions 日志里 `[warn] 未取得数据` 与 raw_fetch 日志表；yfinance 连续失败 → 降级通道（Stooq，见开发方案 §9.7 待办）
- **仓库体积**：db 在 Release 不在 git，唯一会长大的是 gh-pages（orphan 单 commit，恒定 ~1MB）
- **将来加 LLM 生成 narrative**：在 sync 与 render 之间插一步生成 narrative_jp.json 的任务即可，workflow 加一个 step，架构不变

## 5. 本地 vs 云端职责对比

| 环节 | 本地（现状） | 云端（本方案后） |
|---|---|---|
| 定时 | WorkBuddy 自动化（rrule，本机开机才跑） | GitHub cron（云端常驻，不依赖本机） |
| db | `japanstock.db` 本地文件 | Release 资产（每次 sync 后云端自更新） |
| 预览 | 本地打开 HTML | Pages URL 随时可看 |
| narrative_jp.json | 手工编辑 | **仍需手工**：改完 push 到 main，下次 sync 自动带上 |
